## 3.1 概念：手册是入口，不是真值

> **手册回答"这台机器该被怎么用"，不回答"这个函数到底存不存在、参数表长什么样"。
> 所以手册进知识库的第一件事不是"抄进来"，是**分清哪些能抄、哪些抄了等于编**；
> 抄不动的部分，退回外部物证对撞。**"手册里没有"和"我没找到"必须分成两句话。**

第 1 章讲了工厂怎么生成代码，第 2 章讲了真值链怎么跨仓对撞。本章往上游走一层：
**知识库里那些条目是从哪来的**。它是第 1 章的前置——先把手册怎么进来讲清楚，
再看它怎么被消费。

整条入口链是五步：**手册截图 → OCR 文本 → 声明条目 → 外部物证对撞 → KB 条目 → 工厂消费**。
本仓的实现文件是：`ocr.ps1`（30 行）、`gen/adapters_kb.js`（875 行）、`gen/index.js`（152 行）、
`gen/truth_kb.js`（318 行）、`gen/modbus.js`（570 行）。

## 3.2 入口：OCR 只有 30 行，但它定死了"不手抄"

`ocr.ps1` 全文 30 行，用的是 Windows 自带的 `Windows.Media.Ocr`（`ocr.ps1:3-9`），
语言钉死 `zh-CN`（`ocr.ps1:20-21`），取不到引擎就退到用户语言、再取不到就报错退出（`ocr.ps1:22-23`），
最后一行输出识别文本（`ocr.ps1:30`）。技术上没什么可讲的，可它买下的东西很贵：

**手册截图 → 文本这一步从此可复现。** 手抄不是——手抄是"我记得手册上写的是……"，
而这句话永远无法被第三方核验。30 行脚本把一整类争议从"谁记错了"改成"重跑一遍"。

但 OCR 的边界也要说清：**它只出文本，不出真值**。文本还要去撞下一节那几件外部物证。
手册截图是**证据的来源**，不是**证据的等级**——这与第 2 章真值链的纪律是同一条。

## 3.3 三层对撞：PE 导出表 / 官方 C# 绑定 / 官方 C 头文件

知识库文件头把真值来源写死了（`gen/adapters_kb.js:10-15`，逐字）：

> 真值依据（只认这三层外部真值，函数名/参数表/结构体字段顺序全部照抄，不凭记忆）：
> dll_exports.csv    PE 导出表        —— 函数是否存在、是否真的导出
> gts.csv            官方 C# 绑定     —— 函数原型
> gts_hdr.csv        官方 C 头文件    —— 返回类型与参数类型
> gts_structs.csv    官方头文件结构体布局 —— 结构体字段顺序/类型/偏移
> gts_hdr_macros.csv 官方头文件宏表   —— 回零模式号等常量

三层各管一件不同的事：**PE 导出表判"这个符号在 DLL 里真的存在"；C# 绑定判"调用方怎么传参"；
C 头文件判"返回类型与参数类型、结构体布局与宏常量"。** 三层缺一，参数表就会飘。
生成的 P/Invoke 段也把来源挂在代码注释里（`gen/adapters_kb.js:40`，逐字）：

> [真值] 函数名/参数表取自 gts.csv(官方C#绑定) 与 gts_hdr.csv(官方C头文件)，并已对
> dll_exports.csv(PE导出表) 校验

每一条 API 条目都带 `chk`（核对说明，含外部坐标）与 `ok`（是否已核对），例如（`gen/adapters_kb.js:23-24`）：
`{ f: 'GT_Open(channel, param)', use: '打开卡', chk: '官方原型 GT_Open(short channel,short param)（gts.csv:326 / gts_hdr.csv:36…）' }`。
`chk` 里那串坐标就是**锚**——第 2 章说的"每条签名都是主张"，在这里落地成"每条签名都带一个
能当场查的出处"。

**这里有一笔必须如实记的账**：这五份官方件**不在 trae_factory 仓内**。2026-10-22 本机实读确认：
trae_factory 仓内的 csv 只有 `glue_report.csv`（36 行）与其迁居副本；官方件真身在
**mcopilot 仓**的 `knowledge/sdks/official_api/`——`gts.csv`（474 行）、`gts_hdr.csv`（536 行）、
`gts_structs.csv`（218 行）、`gts_hdr_macros.csv`（201 行）、`dll_exports.csv`（12074 行）。
所以工厂条目里那串 `chk` 坐标是**跨仓锚**：它指回上游仓的官方原件。这正是第 2 章真值链
"锚点 = 仓库@commit + 路径"那套办法在跨仓场景下的样子——因此钉扎的验收不靠生成器自述：
`mcopilot@01eb884 scripts/verify_trae_pinvoke.py` 当日实跑退出码 0，58 条 P/Invoke 逐条
`[OK] ← <厂商>.csv:行号`（`decision-lists/trae_factory-2da4559.md:30-31`），
每条都能当场打开官方件核对。

## 3.4 分级：A / B / C 与"未收录降级"

知识库按品牌分级，分级写在两处且必须一致（`gen/index.js:11-19`，逐字节选）：

| 品牌 | 层级 | 标签 |
|---|---|---|
| virtual | A | 虚拟控制器（仿真，零硬件跑通全流程） |
| gts / leadshine / zmotion / acs | B | 四个有官方绑定可对撞的品牌 |
| softwin / gaochuan | C | 骨架 + TODO 清单 |

（同一取值也写在 `adapters_kb.js` 的品牌对象上：`gen/adapters_kb.js:19`/`gen/adapters_kb.js:321`/`gen/adapters_kb.js:487`/`gen/adapters_kb.js:668` 为 `kbLevel: 'B'`，
`gen/adapters_kb.js:802` 骨架为 `'C'`，`gen/adapters_kb.js:857` 虚拟为 `'A'`。）**A 指的是"零硬件能跑通全流程"这一条自证能力**，
不是"厂商资料更全"——分级衡量的是**可交付程度**，不是品牌大小。

58 条 P/Invoke 的构成也要分开报（决策清单 `decision-lists/trae_factory-2da4559.md:33-34`，逐字）："P/Invoke 58 条：知识库钉扎 49 /
未收录降级 9"。**"未收录降级"是一条独立状态**：它在知识库里查得到、但没有被真值链钉住，
所以对外措辞要降级。它既不算"已完成"，也不假装"不存在"。

## 3.5 臆造声明的删除留痕

知识库里最该被学的不是怎么加条目，是**怎么删条目**。

固高适配器里有一条（`gen/adapters_kb.js:37`，逐字）：

> { f: '(未实现) 模拟量 AI/AO', use: '力控模拟量', chk: '官方 C# 绑定与 PE 导出表均无 GT_GetAi/GT_SetAo，已删除该臆造声明；固高模拟量是通道型接口 GT_GetAdc / GT_S…' }

雷赛那边同款（`gen/adapters_kb.js:337`、`gen/adapters_kb.js:382`）："官方 C# 绑定/C 头文件/PE 导出表里都没有 `dmc_set_servo`
（或任何软件使能声明），该臆造声明已删除"。

关键在**手法**：不是把那一行从文件里抹掉（抹掉 = 没人知道曾经错過），而是**把删除写成一条
带核对说明的条目**——`f` 字段明写"(未实现)"，`chk` 字段写清"官方三层都没有，已删除"，
并附上真正的接口名（`GT_GetAdc` / `GT_SetDac` / `GT_PtAo`）与它在官方表里的位置。
读者于是能看见"曾经以为有、现在核掉了"这整段历史。

反例的写法是**猜一个**。第 1 章那批 S 曲线参数就是标准示范（`gen/adapters_kb.js:196-199`，逐字）：

> // [核对] 官方 TTrapPrm.smoothTime 是 short（gts_structs.csv 字段3），
> //        官方真值未给出量纲与取值范围：这里一律填 0（梯形），
> //        S曲线平滑时间必须按手册填写，不臆造换算比例。

——量纲缺失时**唯一合法的出路是回手册**；手册也没写，就填 0 并注明，而不是按经验乘个系数。
"0（梯形）"是一个诚实的降级，"按经验换算的比例"是一个没人能查的编造。

## 3.6 实战案例：两个品牌 0 条 P/Invoke

五品牌套件在 2026-10-22 修复后逐个再生，钉扎结果是（决策清单 `decision-lists/trae_factory-2da4559.md:63-65`，逐字）：

> gts 19/22、leadshine 13/16、zmotion 17/20 钉扎（高川/软赢 0 条 P/Invoke，
> 无真值链可挂属设计事实）；TruthChain.md ×5 全部刷新为现行知识库口径。

"0 条"这两个字是本章最重要的产出。因为**生成器完全可以给高川和软赢也编一套 P/Invoke**——
按行业惯例猜名字、按同类控制器推结构，凑成"五品牌齐全"的交付看起来漂亮得多。
本仓没这么干：这两个品牌交出去的是**骨架 + TODO 清单**（`gen/index.js:17-18` 的标签原文），
`kbLevel` 是 C，`TruthChain` 里没有它们的条目可挂。

代价也要记：19/22、13/16、17/20 三个分数意味着**每个品牌都有一部分 API 没能钉住**；
加上 9 条未收录降级，这套交付的"已核对覆盖面"是 49/58，而不是 58/58。
两头都不好看：能钉的没全钉住，不能钉的干脆不钉。但两面都比"全套已核对"诚实。

还有一层更狠的诚实（决策清单 `decision-lists/trae_factory-2da4559.md:35-36`，T3）："工厂产物的『对』由 mcopilot 官方绑定与编译门
（build_net48.bat 零安装 csc）外部裁决，**生成器自述不作为验收依据**。"——本章第 3.3 节
说的"钉扎"，其裁决权不在写代码的那一方。

## 3.7 习题

**知识题**

1. 三层外部物证（PE 导出表 / C# 绑定 / C 头文件）为什么缺一不可？各判什么？
   *参考*：`adapters_kb.js:10-15`。PE 导出表判"符号真的导出"，C# 绑定判"调用方怎么传参"，
   C 头文件判"返回类型/参数类型/结构体布局/宏常量"。缺 PE 表 → 可能编出不存在��函数；
   缺头文件 → 结构体字段顺序与偏移会错，而这类错编译能过、运行才炸。
2. `chk` 里的外部坐标指向仓外 CSV，这算不算断链？该怎么记？
   *参考*：不算断链，但**不是本仓可验**——五份官方件在 mcopilot 仓
   `knowledge/sdks/official_api/`（trae_factory 仓内 csv 只有 `glue_report.csv` 两份，
   2026-10-22 实读）。正确记法是标成**跨仓锚**（仓库@commit + 路径），并把裁决权交给
   上游仓的 runner（`scripts/verify_trae_pinvoke.py`，58 条逐条 `[OK] ← <厂商>.csv:行号`），
   而不是拿生成器自述当验收。
3. 为什么"未收录降级 9"要单列，不能并进总数？
   *参考*：决策清单 `decision-lists/trae_factory-2da4559.md:33-34`。未收录条目在知识库里查得到但没被真值链钉住，对外措辞必须降级；
   并进 58 就把"已核对"和"存在但没核对"混成一件事。

**反事实题**

1. 若允许在官方三层都查不到时"按同类控制器推一个 API 名填上"，今天会多出多少条 P/Invoke？
   最先被抓住的会是什么？
   *参考*：高川/软赢现在 0 条；放开猜之后这两个品牌会立刻变成"几十条"。
   最先被抓住的是**编译门**（build_net48.bat）与 58 条逐条钉扎的 runner——
   猜出来的名字在 PE 导出表里根本不存在，`[OK]` 变 `[MISSING]`。
   **代价**：一次外部裁决失败就足以让整套交付的可信度归零（第 1 章的"可再生"承诺也一起垮），
   换来的只是"看起来齐全"。
2. 若把 S 曲线的 `smoothTime` 按经验乘个系数填进去（而不是填 0），今天的哪几个数字会变脏？
   *参考*：`smoothTime` 决定轨迹拐角处的加加速度，直接影响 `accel_regime_rms` /
   `decel_regime_rms`（C2 的分域特征）与跟随误差的频谱底噪。
   **代价**：生成的适配器在真机上会"跑得动但形状不对"，而且错得自洽——
   这正是《审计与合规卷》第 7 章《没有真机时》说的"造得诚实"要防的那种不可见的假信号。

## 3.8 可验证主张框 + 讲师切分

> **可验证主张**：为多品牌运动控制代码工厂建立"手册进知识库"的可复现入口链：30 行 OCR 脚本

> 知识库条目一律锚在三层外部物证上（PE 导出表判"符号真导出" / 官方 C# 绑定判"调用方怎么传参" /

> （锚回 mcopilot 仓 `knowledge/sdks/official_api/` 的官方件）、

> 未收录降级 9）；按品牌分级 A/B/C 并两处取值一致；对官方三层查不到的 API **删条目并留痕**

> **高川/软赢 0 条 P/Invoke 交骨架 + TODO 清单**，未把 0 粉饰成"齐全"
